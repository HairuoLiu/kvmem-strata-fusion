**修正要求（三选一，必须显式）**：
1. **恢复原判据并如实报告**：(b) 记为 `NOT RUN`；(c) 记为 `FAIL (abs 1.3310e-5 > 1e-5)`，同时附相对误差作为补充说明。
2. **若认为原判据不合理**，则以**预注册修订**形式记录：写明修订理由、修订日期、修订人，并声明修订发生在看到结果**之前或之后**。事后修订必须标注为 post-hoc。

## 3. 真实模型 P0 的样本量与构造问题

### 3.1 上下文只有 ~512 token / 16 块

`eval_real_model_p0.py:73–89`：
```python
factual_text = ( "In modern systems engineering, ... AlphaDelta9988X. ..." ) * 10
...
num_blocks = seq_len // block_size      # block_size = 32 → 约 16
```

三臂保留率测试循环（`:192–213`）：`num_kv_heads(2) × num_blocks(16)` = **32 个样本**。

**问题**：
- **n = 32**，且是 32 个高度相关的样本（同一段文本的 16 个连续块 × 2 个 head）。
- 保留率是这 32 个值的均值，**无 SD、无 CI、无显著性检验**。
- 以此宣布 "M0 PASSED / T1 Achieved"，统计依据不足。**这一项至少需要 n ≥ 数百，且按层分组报告。**

### 3.2 上下文是同一段落重复 10 次——这不是"真实上下文"

这是本轮最实质的方法论问题：

- `* 10` 意味着 10 个块内容**几乎相同**，是极端的**近重复**场景。
- 长上下文 agent session 的真实分布恰恰相反：块内容**高度各异**（这正是 KVMem 存在的理由）。
- **对 σ 的直接影响**：近重复块会**压低**离散度（块内 token 相似 → `||k_i − k̄||` 小）。他们仍测出 σ_K=8.03，说明该值被 Qwen 的 **massive activation** 通道主导（见 §5），而非语义分散。
- **对针尖检测的影响**：真实长上下文中"针尖"是**统计上的异常点**；而在 10× 重复文本里，异常点是"重复了 10 次的同一内容"。两种分布下 `dev_meta` 的判别力完全不同。

### 3.3 "针尖"出现了 10 次

`AlphaDelta9988X` 在 `* 10` 后出现 **10 次**。这实际上是一个 **10 针尖测试**，而非报告语境中的单针尖 NIAH。与 §2.1 描述的 "Bursty factual token injected at variable depths" 不符。

### 3.4 建议

真实 P0 应当：
- 使用**真实语料**（如 LongMemEval-S / AgentLongBench / PG19 / WikiText-2），而非重复段落；
- 覆盖 **≥4K token**，理想 **≥32K**，并在 256K 上复核；
- 保留"单针尖 / 多针尖 / 干扰针尖"三种形态；
- 每层单独报告 σ 与保留率（现在只有 24 层聚合值）。

### 4.3 最关键的缺失

**他们从未在真实 KV 上运行检测器。**

P0 拿到了真实 σ，却没有把 `dev_meta` 判别力在真实数据上测出来。缺的关键实验是：

> **在真实 KV 上，对"含针尖的块"与"纯背景块"的 `dev_meta` 分布分别作图，看两者是否可分。**

这是**最便宜、最直接**的判别力检验——不需要合成针尖、不需要重排，只需从真实语料里取出若干含实体事实的块，比较其 `dev_meta` 与全分布的位置。

### 4.4 还有一个内部异常

### 4.5 建议

1. 用 §5.2 的真实 σ **重跑** ROC（把扫描范围扩到 σ ∈ [0.5, 20]）。
2. 做 §4.3 的真实 `dev_meta` 判别力实验（最优先）。
3. 报告在真实 σ 下的虚警率与召回率，再决定 θ 的形式。

## 5. σ 的定义偏差与 massive activation 混杂

### 5.1 定义

`:145`：
```python
dev_k = (blk_k - mean_k).norm(dim=-1).mean().item()
```
这是**平均绝对偏差**（mean per-token L2 distance from block mean），不是标准差。但报告全程称其为 "σ"（§5.2 标题 "Real Token Dispersion (σ) Measurements"）。

这与我们合成数据里的 "σ ≈ 0.02"（噪声标准差）**不是同一个量**，二者不可直接比较。§4.2 用 σ 扫虚警、§5.2 用"σ"报实测值，两处口径不同却并置讨论。

**建议**：统一记号。合成用 `σ_noise`，实测用 `D_mean` 或 `MAD_block`，明确区分。

### 5.2 massive activation 混杂

σ_V=4.93、σ_K=8.03。Qwen2 系列已知存在**massive activations**——少数通道的激活值远超常规（attention sink token 尤甚）。以 L2 距离衡量离散度时，**少数异常通道会主导整个数值**。

**这意味着 σ_K=8.03 很可能不是"语义分散度"，而是"异常通道幅度"。**

后果：`θ = μ_block + 3.2σ_block` 的阈值由异常通道决定，**与"是否含针尖"无关**。

**建议补测**（都在同一份 dump 上，几乎零成本）：
- 逐通道分解：`var` per channel，报告 top-5 通道贡献了 σ 的百分比；
- 剔除 top-k 异常通道后的 σ；
- 逐层 σ 分布（现在只有 24 层聚合）；
- 对 `k` 做 L2 归一化后再算 σ。

### 5.3 K/V 比值的解读要谨慎

他们写"σ_K/σ_V = 1.63×，confirming the KIVI K/V asymmetry on Qwen"。KIVI 的结论是 **K 适合 per-channel、V 适合 per-token** 量化，这是**码本分配**的不对称，不是**幅度**的不对称。幅度比 1.63× 不能直接印证 KIVI 的结论。

**建议**：要么补 KIVI 的量化配置对比实验，要么把这句话改成"观察到幅度不对称（1.63×），尚待与 KIVI 的 per-channel/per-token 分配做对应验证"。

## 6. 误差分解为压缩开脱，却给检索定罪

### 6.1 结果与解读

§4.1 三数：

| 对比 | 值 | 含义 |
|---|---|---|
| cos(Oracle, Full) | 0.2830 | **纯截断损失** |
| cos(IFR, Oracle) | **0.9980** | **纯压缩损失**（极小） |
| cos(IFR, Full) | 0.2730 | 合计 |

他们据此写 "**Definitive Proof**：压缩保真 99.8%，0.28 几乎全部由稀疏截断驱动"。**这个分解方法是对的，压缩侧确实不是问题。**

### 6.2 但结论指向了一个他们没接着追问的问题

cos(Oracle, Full)=0.283 意味着：**用检索到的 16 个块算出的 attention 输出，与全量上下文的 attention 输出只有 0.28 相关——73% 不相关。**

他们把这写成"截断决策的责任，与量化无关"。这个说法在**归因上正确**，但在**结论上回避了真问题**：

> 研究问题是"只检索一小部分块是否可接受"。0.28 说明在当前 K 预算下，**检索决策本身**才是主要误差源。压缩环节几乎无损，并不意味着方案可用。

这恰恰是 v1 F 门设立的原因：**检索代理指标满分（召回 100%、压缩保真 99.8%）不等于端到端可用**。

**建议**：把 §4.1 的结论改写为——"压缩环节已排除为误差来源（0.9980）；**下一阶段的问题转移到了检索预算**：需在真实模型上确定 cos(Oracle, Full) 随 K/N 的衰减曲线，并找到满足端到端保真所需的最小 K。"

### 6.3 配置漂移：K 值不一致

## 7. 索引明细遗漏 L × H_kv（主导项）

### 7.1 他们的明细（§4.3）

| 组件 | 每块字节 |
|---|---|
| 质心向量 (64 × 4B) | 256 |
| posting 节点 (uint32 + uint32) | 8 |
| Merkle 前缀哈希 (SHA-256) | 32 |
| 块元数据 (dev_meta, tier_id, refcount) | 32 |
| **合计** | **328 B/块 ≈ 10.25 B/token** |

### 7.2 问题：Mean-K 检索必须**逐层逐头**打分

`kvmem` 的 Mean-K 索引定义是"剥 RoPE 后按 **(layer, KV head)** 取块内均值"。因此索引必须在每个 **(layer, head)** 上各存一份质心。

以 Qwen2.5-0.5B（**L=24 层，H_kv=2 头，d=64**）计算，每块质心数量应为：
```
24 × 2 × 64 = 3,072 个值
fp32: 12,288 B/块 = 384 B/token
fp16:  6,144 B/块 = 192 B/token
```
**是他们 328 B/块  accounting 的 12–24 倍。**

他们的明细等于假设"每块只存一个 64 维质心"。这只有两种可能：
- **(a) 索引是跨层共享的**（layer-agnostic）——那么逐层打分无法进行，召回会受损；或
- **(b) 明细漏算了 L × H_kv 因子**——数字需要重算。

### 7.3 对 85× 差异的解释是推测

他们写："KVMem Table 4 Heavyweight Index preserves token-level positional inverted indexes and embedding projections for full lexical replay (~1024 bytes/token)"。

KVMem 论文并没有这个说明。这是**事后推测**。而 85× 差距更可能由我们早已指出的原因造成（A3 / R8）：

> **层数 L 才是索引体积的杠杆**（index/KV = 1/(2B)，与 head 数无关）。

所以正确的对账方式是：把 L×H_kv 因子代入，看能否解释差距，而不是引入一个未见于论文的"词法重放"机制。

### 7.4 实际影响：Gate C 仍通过，但结论需修正

- 他们 10M：328 B × 312,500 块 ≈ 102 MB
- 补上 L×H_kv（fp16, L=24, H=2, d=64）：约 1.8 GB @10M
- Gate C 判据是 **≤ 4 GiB** → **两者都通过**

所以这**不是 Gate 失败**，但：
1. "well within Gate C，余量 40 倍"的说法需要修正（实际余量约 2 倍）；
2. 索引规模的正确模型是后续 UBBA 字节预算的输入，**算错会直接误导档位分配**；
3. "layer-agnostic 索引"若真是设计选择，则它是一个**与召回率强相关的架构决定**，必须单独评估，不能藏在字节明细里。

## 8. 统计契约：实现正确，但配对检验用了非配对 SE

### 8.1 正确的部分（已验算）

见 §1 末段——Wilson、McNemar N=471、Deff=1.9、OBF alpha-spending 均正确。

### 8.2 问题：`evaluate_interim_look` 用了非配对 SE

`stopping.py:89–92`：
```python
p_pool = (successes_a + successes_b) / (2 * total_tested)
se_raw = np.sqrt(p_pool * (1 - p_pool) * 2 / total_tested)
se_adj = se_raw * np.sqrt(self.design_effect)
z_stat = diff / (se_adj + 1e-12)
```

这是**独立样本**的 SE 公式，完全没有用到配对信息。但整个 harness 的目的（`compute_mcnemar_sample_size` 里 π_d=0.15）就是配对设计。

McNemar 检验的正确方差基于**不一致对（discordant pairs）**：设 b、c 为两类不一致对，
```
diff  = (c − b)/n
Var(diff) = [ (b + c) − (c − b)²/n ] / n²
```
当前实现的后果：
- 同任务不同 seed 的配对**相关性很强** → 不一致率低 → **正确的 SE 更大**；
- 使用非配对 SE 会**低估方差**，使 `z_stat` 偏大 → **边界过于宽松 → 提前停止**。
- 也就是说，这个 OBF harness 会比正确实现**更容易宣布阳性**。在一个序贯检验里这是方向性错误。

同时 `p_a`、`p_b` 用 `successes/total_tested` 各自计算再相减，也不是配对差的正确估计（应只用 discordant 对）。

**另外**：`compute_cluster_design_effect(4, icc)` 在 `:77` 把 m=4 写死，未暴露为参数。

**建议**：
- 直接接受 (b, c) 不一致对计数作为输入，按 McNemar 方差计算；
- 把 `num_seeds_per_task` 暴露为参数；
- 加单元测试：**用模拟数据验证 harness 的 FWER ≈ 名义 α**（这是序贯检验唯一可信的自检）。

## 10. 【自我纠正】我们的 82% 高频维损失论证被他们的真实数据推翻

这一节是**我们自己要改的**。

我们 LADDER 报告 §3.2 论证：32-token 块跨 Δθ=32 rad ≈ 5.09 个整圈，32 个近随机相位单位向量平均后期望模长 ≈ 1/√32 = **0.177**，即**高频维损失 82%**。据此断言"必须先 de-RoPE 再合并"。

**他们在真实 Qwen2.5-0.5B 上测得 Arm A 保留率 = 0.4430**（见 §5.3 表）。

即真实损失约 **56%**，而非 82%——**我们的相位均匀近似高估了危害约 2.5 倍**。

补充一个更尖锐的事实：`plan-02` §4.1 的合成单元测试给出 **0.1612**，与我们的 0.1768 高度吻合。也就是说——**我们的论证只被一个按同样近似构造的合成 harness "验证"过，而真实模型直接推翻了它**。这类"用合成数据验证解析论证、从不与真实模型对表"的循环，正是本轮 v3 要求补 P0 的原因。

**这有三个后果，我们必须自己承担：**

1. **"必须 de-RoPE"的紧迫性下降。** 若直接平均仍保留 44% 模长，它对检索可能已经够用。LADDER L2′ 的价值主张从"必需"降级为"有益"。
2. **这也解释了他们 B/A = 2.14× 而非我们预期的 ~5.7×**（0.9481 / 0.166）。比值有限是**因为分母被高估了**，不是因为分子不行。
3. **建议改写 LADDER 的论证**：把"82%"改为"在真实 Qwen2.5-0.5B 上实测 56%（0.4430 保留率）；相位均匀近似给出 0.177，是上界而非期望"。并补一条：**在真实 KV 上直接检验 44% 保留率是否足以支撑检索**（即 §2 的 recall@64 实验）。

**这一条削弱了我们自己方案的必要性论证。** 把它写进来，是为了让这份评审可信——否则我们只是在挑别人的错。
